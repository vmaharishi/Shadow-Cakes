## Long-term data behavior
- **Refresh policy**: None. All data is user-entered or user-imported inside the artifact; no external feed, no scheduled refresh.
- **Growth**: Rows accumulate as the user adds ingredients, prices, recipes, sales; imports replace their whole table set, matching the original.
- **Ordering**: Sales newest first by sale_date; ingredients/packaging/components/recipes alphabetical; price history newest purchase first with the latest flagged.
- **Time semantics**: Dates are user-entered calendar dates (purchase_date, sale_date) stored as ISO date strings and rendered as entered — no timezone conversion. Settings is a single row seeded with the original defaults ($10/hr labour, $1/hr utilities, CAD $) on first read, editable thereafter.

## Imagery
Imagery not needed: this is a data-entry/costing tool whose surfaces are tables, forms, and numeric breakdowns; the original's only images were decorative Unsplash empty-state photos on expiring-prone remote URLs, and empty states here use warm typography and iconography instead. No photos depict real items the user must recognize.

Photo scan explicitly out of scope (deferred by the user). All test rows were sandbox-only; the live dataset was never touched.
- **Bugs found & fixed**:
  1. *Ambiguous import dates shifted by months* — a day-first date with both parts ≤ 12 (e.g. "05-06-2025") fell through to `new Date()`, which parses month-first. `impDate` now reads the DD-MM-YYYY shape day-first (only the forced month-first shape, second part > 12, is honoured). Verified: "05-06-2025" imports as 2025-06-05.
  2. *Small percent margins corrupted on sales import* — the "≤1 means decimal fraction" rule turned a genuine 0.5% margin (Sales-page CSV export format) into 50%. The importer now disambiguates against the row's own profit ÷ selling price and keeps whichever reading matches. Verified both ways: 0.5 stays 0.5; 0.32 still becomes 32.
  3. *Merge re-import wiped cost history* — updating a recipe via merge import regenerated every variant id, orphaning all cost snapshots keyed by the old ids (the recipe view showed no history). Same-named variants now keep their existing ids on merge update. Verified: history chain intact plus a new "Data imported (merge)" snapshot under the same variant id.
  4. *Deleting the latest price left no latest price* — costing fell back silently but the UI showed no flagged latest. `deletePrice` now promotes the most recently purchased remaining price. Verified in the price list.
  5. *Cost breakdown silently understated totals* — ingredient lines with no price, and packaging/component lines whose item was deleted, were skipped with no signal. `variantCost` now returns `missing_lines` (including unpriced lines inside a component, prefixed with its name), the recipe detail shows a named warning above the total, and a dangling price-override id no longer flags the line as "Override" when the fallback price is what's used.
  6. *Workbook backup lost priceless ingredients* — the Ingredient Pricing sheet only wrote rows for prices, so an ingredient with no prices vanished on restore. The export now writes a name-only row for it, and the importer reads a name-only row (no price and no size) back as a priceless ingredient with a clear warning instead of a skip.
  7. *Components CSV export dropped packaging* — the per-page CSV wrote only ingredient lines. It now writes every line with an explicit `line_type` column (the format the components import reads), metadata on the first row.
  8. *Packaging edit silently stamped a date* — editing a packaging item with no purchase date defaulted the form to today and saved it. The form now keeps dateless items dateless; only new items start at today.
  9. *Silent no-op updates & orphan prices* — `updateIngredient`/`updatePackaging`/`updateRecipe`/`updateComponent`/`updateSale` now throw a clear "not found" error when the id doesn't exist (via `.returning()`), and `createPrice` rejects a price for a nonexistent ingredient.
  10. *Replace-import dangling references unmentioned* — replacing Packaging or Components alone (without Recipes) now warns, like Ingredients already did, that existing recipe lines will stop costing until re-imported or re-picked.
  11. *Settings form accepted non-numeric rates* — text like "abc" passed validation and saved as $0 (parseFloat NaN slipped past the `< 0` check). It now rejects NaN explicitly.

## Bug fix (Nov 22, 2026 — "Prepare workbook" in Settings → Data fails, user-reported)
- **Symptom**: tapping "Prepare workbook" errored and no file could be exported. Reproduced exactly via the action: `prepareWorkbookBackup` (and `exportWorkbookData`, and `listComponents`) threw `TypeError: undefined is not an object (evaluating 'l of v.ingredients')`.
- **Root cause**: data corruption from migration 0006, not the download delivery. Her components were imported at 20:53 UTC under the pre-variants build (rows like "Dark Chocolate Ganache — 6-inch"); when the Stage 5 build deployed at 21:09 UTC, migration 0006 merged them and built the `variants` JSON — but in the live database each array element landed as a JSON **string** (`["{\"id\":…}"]`) instead of an object, despite the `json(...)` wrap that tested correctly in the sandbox. Every reader looping `variant.ingredients` then crashed: the Components page, the cost engine, and the workbook builder. Recipes, ingredients, and sales data were unaffected (verified: `listRecipes` and the dashboard totals are healthy).
- **Fix (two layers)**: (1) migration `0007_repair_component_variants_stored_as_strings` rewrites any `component_recipes.variants` whose first element is text, via `json_group_array(json(je.value))` over `json_each` — tested against the actual corrupted live values in Bun's SQLite: both components come back as objects with all lines intact (Ganache 6-inch: 7 ingredients, 623 g yield). (2) `componentVariantsOf` — the single choke point every component reader goes through — now parses string elements back into objects and defaults missing line lists/numbers, so this encoding can never crash costing or exports again even if it recurs.
- **Verified in the sandbox** (clone of live data): after the fix, `prepareWorkbookBackup`, `exportWorkbookData`, and `listComponents` all succeed against the corrupted rows even before the repair migration runs.

## Bug fix (Nov 22, 2026 — "Save workbook" kills the space on the Mac app, user-reported)
- **Symptom**: after Prepare succeeds, tapping "Save the workbook" showed the shell's "Couldn't load this space. Try again." error — every time, on the Mac app. The action itself was verified healthy (returns the dated filename, ~56.5 KB, and a `./blobs/` URL).
- **Root cause**: the Save control was a plain `<a href={blobUrl} download>`. Following it navigates the webview to the blob URL, and blob responses are deliberately served with a sandbox CSP and `nosniff` — a top-level navigation to one cannot render as a page, so the shell's load failed and it replaced the whole space with its error screen. The file was never the problem; the navigation was.
- **Fix**: nothing in the artifact navigates to a blob URL anymore. On Prepare success the client immediately fetches the prepared file's bytes in-page (fetching a blob URL is unaffected by the sandbox CSP — the same mechanism that loads recipe photos and PDFs) and caches the Blob. "Save the workbook" is now a button that hands those bytes to the existing `triggerDownload` (attached anchor, object URL kept alive 60 s) synchronously inside the tap, so no async gap can lose the gesture. If the prefetch failed, Save/Share fall back to fetching on tap, then to building the file client-side from `exportWorkbookData` — the exact bytes either way, since both come from `buildWorkbookSheets`. The Share button now also reuses the server-built file instead of rebuilding client-side. `prepareWorkbookBackup` is unchanged apart from its description; it still stores the canonical server-built file.

## Bug fix (Nov 22, 2026 — "Save workbook" silently does nothing, third report, user-reported)
- **Symptom**: Settings → Data → "Prepare a fresh copy" → "Save the workbook" → nothing downloads, no error. Server-side prepare verified good again (he reaches the Save step); the failure is purely client delivery inside the Muse in-app webview.
- **Root cause**: the previous fix made "Save the workbook" a programmatic click on an `<a download>` pointing at a blob: object URL (`triggerDownload`). In-app webviews (WKWebView / Android WebView in the Muse app) do not implement blob-URL anchor downloads — the synthetic click is dropped silently, yet the UI toasted "Workbook download started", a success claim for a file that never arrived. The one mechanism that did work, the Web Share sheet, was demoted to a secondary button and routed through an async fetch before calling `navigator.share`, risking loss of the tap's user gesture that `navigator.share` requires.
- **Fix**: delivery is now share-first. On Prepare success the client fetches the bytes in-page (unchanged) and immediately builds a `File` held in state. The primary "Save the workbook" button, when file sharing is available (`navigator.canShare({files})`), calls `navigator.share({files})` synchronously inside the tap — the OS share sheet's Save to Files is a native hand-off that doesn't depend on the webview's download handling. Where file sharing is unavailable (most desktop browsers, which honour anchor downloads), it falls back to `triggerDownload`. A secondary "Download instead" button keeps the plain browser download. The toast is gone; a persistent status line under the buttons reports only what actually happened — share completed, share sheet dismissed without saving ("the workbook isn't saved yet"), or a browser download started (with a pointer back to Save to Files if no file appears). No platform file-delivery API exists in the space SDK (checked `client.d.ts` — no download/share helpers), so Web Share is the most robust mechanism available in this environment.

## Bug fix + layout (Nov 22, 2026 — quote Download silently does nothing, user-reported; then superseded by the user's Share decision)
- **Symptom**: Quote Preview → Download showed "Download started — look for the quote image in your downloads" but no file ever arrived. Same root cause as the workbook saga (see the third Save-workbook fix above): the button fired a programmatic blob-anchor click (`triggerDownload`), which the Muse in-app webview silently drops, while the status line claimed success unconditionally.
- **User decision (supersedes the Send/Download pair)**: on mobile both buttons ended at the same native share sheet anyway, so the Preview now has ONE action — **Share**. It opens the phone's native share sheet with the pre-rendered image File ONLY (no title/text/URL, via `shareFileOnly`), invoked synchronously inside the tap from the pre-rendered File; from the sheet she can send it (WhatsApp, Messages, Instagram…) or keep a copy via the sheet's own Save Image / Save to Files. The Download button, `onDownload`, and the "Download started" line are gone. Share stays disabled until the image File is rendered, so it can never promise an action it can't perform. Where a browser has no file sharing at all (some desktop browsers), Share falls back to a plain browser download with an honest one-line status. The page intro now reads "share the quote as an image with your customer".
- **"On this quote" rows stacked (user-directed)**: each row is now two lines — item name + variant at full width on the first line with the remove × at its right end, and the $ price field on the line underneath — so long names ("Vanilla Chiffon Cake · 6-inch") no longer break mid-variant. One shared row component, so it applies at every width.
- **Settings tabs on one line (user-directed)**: the Costs / Backup / Upload / Chat setup tab bar is `flex-nowrap` with `shrink-0 whitespace-nowrap` pills at 13px with tighter padding on phones (full size from `sm` up) — all four fit on one line at phone and desktop widths.
- **Quote-page scan (phone + desktop, probe-driven, sandbox only)**: banner thumbnails render, select and "Use no banner" both work and the Preview renders the banner and no-banner (logo-pair) images correctly; search-only Add items filters, expands, and the per-variant tick adds the row; a price edit saved (Tiramisu → $53) and a row remove worked; the footer editor typed, saved ("Saved — every quote image uses this text until you change it"), and the saved text is what the next quote image renders. No console errors, no broken images, no overflow anywhere on the page. One behaviour noted: right after changing the banner, the Preview can briefly show the previous image while the new one re-renders (the pre-render is debounced ~350ms plus render time, slower in the sandbox where font loads are blocked); the image shown and the file Share hands over are always the same File, so what she sees is what gets sent.
